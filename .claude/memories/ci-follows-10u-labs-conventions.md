# CI follows the 10U-Labs conventions

CI is written the way deltahdl (`../../deltahdl/deltahdl`) and the 10U-Labs repos (`../../10U-Labs/*`) write theirs:

- One workflow per thing it guards, named after it: `release.yml` for the compiled Rust product, as the 10U-Labs tools name theirs (deltahdl calls its own `deltahdl.yml`), and `markdownlint.yml` for the Markdown. Each starts on a push to `main` filtered by `paths`, and on `workflow_dispatch`, with a `concurrency` group that cancels older runs.
- Every workflow checks itself: its own `assert-no-comments` and `yamllint` jobs cover the workflow file, and `yamllint` also runs `assert-no-inline-directives --tools yamllint`.
- Because Rust is compiled, the product workflow builds once per platform and the test tiers consume that build, as deltahdl does with CMake: `build-<platform>` writes a `cargo nextest archive` and uploads it, and `unit-test-<platform>`, `integration-test-<platform>` and `e2e-test-<platform>` each need `build` alone, so the tiers run side by side. Lint checks (`clippy`, `rustfmt`, the asserts) are their own jobs with no `needs:`. Each build leg also compiles `hgm` and `hgm-agent` with `--release` and uploads them as `release-<platform>`. A `release` job, on a push to `main` once every other job has passed, tags `v<UTC %Y%m%d%H%M%S>`, publishes a GitHub release with `--generate-notes` and the release binaries (`<bin>-<platform>`), and force-moves the `latest` tag, as deltahdl and the 10U-Labs tools do.
- Code limits mirror deltahdl, except that the file limit is 1000 lines rather than deltahdl's 949. `assert-no-oversized-source-files` fails any `*.rs` file in src/test/lib over 1000 lines. Clippy carries the clang-tidy limits: cognitive 15, arguments 5, nesting 5 (clippy counts the function body, so this equals clang-tidy's 4), and lines 200 in src or 300 in tests. The thresholds are in `etc/clippy/{src,test}/clippy.toml` and the levels in `[workspace.lints.clippy]`. The `clippy` job runs twice: `--lib --bins` with `CLIPPY_CONF_DIR=etc/clippy/src`, and `--tests` with `etc/clippy/test`. The assert jobs are also adapted to Rust: `assert-file-and-registration-sets-agree`, `assert-no-empty-test-files`, `assert-no-inline-directives` (a grep for `#[allow]`-style attributes) and `assert-no-linter-config-files`. Fix code rather than raise a threshold. Formatting is rustfmt's defaults (the Rust Style Guide), with no rustfmt.toml. CI only asserts it (`cargo fmt --all --check` plus `rustfmt --check` on every *.rs file), as deltahdl asserts clang-format with --dry-run --Werror; run `cargo fmt` locally before pushing. `nonstandard_style` is denied in the workspace.
- Coverage is split the way deltahdl splits it, on Linux x86_64 and stable Rust only. `build-coverage` builds the instrumented test archive once (`cargo llvm-cov nextest-archive --workspace --all-targets`) and uploads it as `build-coverage`. `unit-test-coverage`, `integration-test-coverage` and `e2e-test-coverage` each need `build-coverage` alone, run their tier from the archive with the plain tier job's filter (`cargo llvm-cov nextest --archive-file … --no-report`, `LLVM_PROFILE_FILE_NAME=<tier>-%p-%m.profraw` so names never collide), and upload `profraw-<tier>`. `assert-coverage` needs those three, builds and runs nothing: it unpacks the archive into `target/llvm-cov-target`, downloads every `profraw-*` there, uploads the `coverage-html` report and requires 100% of lines, functions and regions outside `test/` (`cargo llvm-cov report --nextest-archive-file`). `release` waits on it. The plain tier jobs still run on both platforms, so every test runs twice on Linux x86_64, once instrumented and once plain. Everything stable Rust can measure is covered; nightly is never used, not even for branch coverage. New code lands with its tests at full coverage. Check locally with `cargo llvm-cov nextest --workspace --no-report && cargo llvm-cov report --ignore-filename-regex '(^|/)test/' --show-missing-lines`.
- An assert with a published action runs through it (`10U-Labs/assert-no-comments@latest`). `yamllint` uses the 10U-Labs rules (`empty-lines` max 0, `key-ordering`, `line-length` disabled, `new-line-at-end-of-file`, `truthy` allowing `on`) with `--strict`, so a workflow starts with `---`, has no blank lines, sorts every mapping's keys, and names every step.

**Why:** The 10U-Labs repos are the reference for how workflows are split and named, and deltahdl is the reference for how a compiled language splits its build from its tests.

**How to apply:** a new kind of file gets its own workflow rather than a job in `release.yml`. Before inventing a CI pattern, look at how those repos do it. Related: [[supported-platforms]], [[no-comments-in-any-file]], [[always-use-latest-versions]].
